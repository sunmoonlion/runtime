## 冲突

1. SDD 0022 第一、三节和任务页：服务流单帧上限 1 MiB；`fs/readFile` 默认及最大 `length` 也是 1 MiB，结果为单个 JSON-RPC 文本消息，`content` 用 base64。
2. 任务页真机验收要求读取 5 MiB 文件分 5 段。
3. `relay.py:50` 固定 `SERVICE_MAX_FRAME = 1024 * 1024`；`:356` 对工作台→代理和代理→工作台两方向均应用该上限；`:413` 起的 `_pipe` 遇到超限消息关闭代理侧，码 1009，不透传。
4. 1 MiB 原始数据 base64 后为 1,398,104 字节；本次按合同构造的 JSON-RPC 回包为 1,398,189 字节。即使原始内容全为零、路径和消息都用 ASCII，仍必然超限。WebSocket 分帧不会解决应用按完整消息检查的问题。

不能把请求偷偷改为更小分段，也不能放宽会合点门禁后声称合同原样通过。

## 实际复现

命令：`runtime/.venv/bin/python /tmp/sunmoon-service-frame-check.py`，退出 0。
使用 Python websockets 17.1，加载上述固定 k8s 提交中的 `Relay` 类，在回环随机端口启动现有 handler。测试控制端声明 `service-v1`，工作台连 `/service`，按 `open.kind=service` 连接 `/agent-data`，完成真实配对。静态令牌为本探针专用的无权限测试值，未使用任何账号凭据。

先发 1 字节内容的合法回包，工作台原样收到；再发含 1 MiB 合成零字节的合法 base64 回包，工作台未收到内容，代理数据连接收到关闭码 1009。仅记录计数和关闭码，不记录文件路径或文件内容。

原文输出：

```text
{"agent_data_close_code": 1009, "base64_bytes": 1398104, "json_response_bytes": 1398189, "large_response_forwarded": false, "raw_read_bytes": 1048576, "relay_frame_limit": 1048576, "small_response_forwarded": true, "workbench_close_code": 1000}
```

复跑要点：使用 `bytes(1024 * 1024)` 的 base64 作为 `result.content`，同时含 `size=1048576, mtime=0, eof=false`；调用现有 `Relay.handler` 配对，发送 JSON-RPC 文本响应，检查是否被透传和两侧关闭码。不得用改过限额的 relay 代替。
